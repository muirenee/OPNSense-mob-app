# Netsource Sentinel — Play Console Submission Checklist

This checklist is the release gate for the first public Google Play submission.

## 1. Developer account
- Complete Google Play developer identity verification.
- Prefer an Organization account when publishing under a company/brand.
- Confirm the public developer name, support email, phone and website.
- If the account is a newly created personal developer account subject to Google's testing rule, complete the required closed-test period and tester count before requesting production access.

## 2. App identity
- App name: **Netsource Sentinel**.
- Android application ID: **com.netsource.sentinel**.
- Do not create a Play app under the older development ID `com.netsource.netsource_opn_manager`.
- Keep the permanent package ID unchanged after the first Play creation.
- Version 1.0.0 uses versionCode/build 100.

## 3. Android release
- Target Android 16 / API 36.
- Build and upload the signed `app-release.aab` from the permanent release pipeline.
- Enroll the application in Play App Signing.
- Store the upload/release keystore and credentials securely outside Git.
- Confirm the expected upload certificate before the first production release.
- Retain an independently backed-up copy of the upload key material.

## 4. Store listing
- App name and short description.
- Full description.
- App category: Tools.
- 512 x 512 high-resolution PNG app icon.
- 1024 x 500 feature graphic.
- At least two representative phone screenshots; four or more are recommended for a stronger listing.
- Avoid screenshots containing secrets, private firewall addresses, customer names or production credentials.
- Localize later after the English listing is approved.

## 5. Privacy and legal
- Publish the Privacy Policy on a public HTTPS page that is accessible without login.
- Configure that public URL in Play Console.
- Keep the same privacy policy accessible from inside the app.
- Complete the Data Safety questionnaire consistently with actual app behavior.
- Review and publish the EULA/Terms page.
- Maintain Third-Party Notices for Flutter packages and OPNsense interoperability/trademark notice.
- Have the commercial EULA and privacy text reviewed by qualified counsel before broad paid distribution.

## 6. Data Safety working assumptions for v1.0
Validate these against the final binary and licensing backend before submission:
- Firewall API keys/secrets: stored locally; not sent to Netsource licensing service.
- Firewall profile URL/name: stored locally by the app.
- Installation identifier: randomly generated by Sentinel and sent to the licensing service when licensing is activated/refreshed.
- Activation code / opaque lease token: used for license administration.
- App package/version/build: sent to licensing service with activation/refresh.
- No advertising SDK in the current dependency set.
- Demo Mode: local sample data only.

Do not copy these assumptions blindly into Play Console after adding analytics, crash reporting, billing, authentication or any other SDK; re-audit Data Safety whenever dependencies or backend behavior changes.

## 7. App access / reviewer instructions
- State that no login is required for Demo Mode.
- Reviewer path: launch app → **Explore Demo Mode**.
- Explain that Demo Mode does not contact or change a firewall.
- If Google requests access to a gated commercial feature, provide dedicated test entitlement credentials/code that cannot affect production systems.

## 8. Content and declarations
- Complete Content Rating questionnaire accurately.
- Declare target audience accurately; this is an administration tool, not a children's app.
- Complete ads declaration: no ads if the final binary still contains no advertising.
- Complete any required government/financial/health or other special declarations as “not applicable” only when accurate.
- Review permissions in the final manifest; v1.0 currently requires Internet access and should avoid unnecessary sensitive Android permissions.

## 9. Testing tracks
- Upload v1.0 AAB to Internal testing first.
- Install from Google Play on at least two physical Android devices when possible.
- Test package update behavior for subsequent build numbers.
- Test Demo Mode with no network connection.
- Test real firewall connection over LAN/VPN and HTTPS.
- Test self-signed option only against a controlled test firewall.
- Test dark/light/system appearance.
- Test license activation, refresh, offline grace and deactivation when production licensing API is available.
- Promote to Closed testing before Production when required by the account or when broader validation is desired.

## 10. Production release gate
Do not promote to production until all of the following are true:
- CI Analyze and all tests pass.
- Signed APK verification passes.
- AAB exists and `jarsigner -verify` succeeds.
- API 36 target confirmed.
- Demo Mode reviewed end-to-end.
- Public Privacy Policy URL is live.
- Data Safety form matches actual behavior.
- Final store icon/feature graphic/screenshots are uploaded.
- Licensing backend production URL is configured if paid activation will be enabled at launch.
- No test activation codes, production firewall credentials or signing secrets are committed to the repository.
- EULA/privacy have received appropriate business/legal review.

## 11. Post-launch
- Monitor Play pre-launch reports and Android vitals.
- Respond to crashes and API compatibility regressions.
- Keep OPNsense version-compatibility notes current.
- Increment versionCode for every Play upload.
- Re-run privacy/Data Safety review whenever data handling or SDKs change.
